## 1. Refactorización de Seguridad (UserDetails)

### UserDetailsServiceImpl - Clase Unificada

Se unificaron las clases `NormalUserDetailsService`, `SuperAdminUserDetailsService` y `CustomUserDetailsService` en una sola clase con comentarios detallados:

```java
@Service
@RequiredArgsConstructor
public class UserDetailsServiceImpl implements UserDetailsService {

    // Login normal de empresas - con filtro tenantId
    public UserDetails loadUserForNormalLogin(String username, Long empresaId) {
        // Busca: WHERE nombre_usuario = ? AND empresa_id = ?
        // Excluye ADMINDEV
    }

    // Login superadmin - sin filtro tenantId
    public UserDetails loadUserForSuperAdmin(String username) {
        // Busca globalmente
        // Valida que sea ADMINDEV
    }
}
```

### SecurityConfig
- Actualizado para usar la nueva clase `UserDetailsServiceImpl`
- Mantiene los dos filter chains (Order 1: superadmin, Order 2: empresas)

### Repository
- Activado `findBynombreUsuario()` en `UsuarioRepositorio`
- Activado `existsByRol()` en `UsuarioRepositorio`

## Consideraciones Técnicas

### Patrón DTO
- **Usuario**: Request/Response separados (para API REST futura)
- **Producto, Ingrediente**: Un solo DTO (compatible con vistas Thymeleaf)

### Auditoría
- Los logs se guardan en `./logs/audit/audit.log`
- El usuario se obtiene de `SecurityContextHolder`
- Cada método del service registra su acción

### Multi-tenant
- Todos los repository methods filtran por `empresa.id`
- El `tenantId` se obtiene de `TenantContext.getTenantId()`
- Si no hay contexto, se lanza `BusinessException`

### Testing
- Mockito + JUnit 5 puro
- DataProviders estáticos para datos de prueba
- @BeforeEach para configurar `TenantContext.setTenantId()`
